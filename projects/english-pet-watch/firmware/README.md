## 拖动圆形变形：扫描同步相位（2026-11-19）

上一版数字截图中圆形像素一致，不能排除实屏扫描将移动图标显示成两段。此版修正 TE 时机，未改横纵缩放比例，实屏圆形是否彻底稳定仍标记为待验证。

- 由 TE 上升沿（空白期）改用下降沿（有效扫描开始），收到新信号后等待约四分之一扫描周期，再发送当前帧首块；实测 16.7ms 周期时软件延时设为 4ms，实际调度约 3–4ms。仍只在首块等待，沿用 35ms 超时、连续三次缺失回退和计时回绕处理。
- 保留两块 24 行内部 DMA 缓冲、原局部刷新、图标缓存及 90% 位移阻尼。没有增加 PSRAM 常驻占用、修改图标大小或降低颜色精度。
- 已排除两条实机效果较差的路线：整帧 PSRAM 直传出现 DMA 欠载错误；使用内部中转后整帧版仅约 14 次绘制/秒。强制全屏顺序局部刷新也仅约 18 次/秒，且存在长帧。这些测试改动均不保留。

最终候选实测：相同八秒快速轨迹，202 帧/8.028s（25.2 次绘制/秒），2244 次局部送屏，越界矩形 0，202 帧完成回调；首块发送到末块 DMA 完成平均 11.3ms、最长 29.7ms。无 DMA 错误、看门狗或崩溃；联网成功。此值不是光学帧率，不能据此宣称实屏变形已消失。相对上一版约 28 次/秒存在时序调整后的吞吐量代价。

验证：`cd ui_demo && python3 tools/test_firmware.py`（58 项通过），加载 ESP-IDF 后 `idf.py build`。测试覆盖延时有效周期范围、一次等待、超时回退、回绕及托管 BSP 幂等配置。⚠️ 使用稳定 USB 供电、音量保持 0；本次只读取数字信号和性能统计，没有导出新截图。临时轨迹、计时钩子及下载的数据手册副本已清理，正常固件不包含测试入口。正式固件已烧录并通过写入哈希校验，启动实测 TE 周期 16746us、响应年龄 3177us，内部空闲约 30.7KB、PSRAM 约 3.05MB，无新显示传输错误。扫描变形的光学验收仍待验证；不涉及 BOM、接线、外壳或重打印。

## 快速拖动绘制性能（2026-11-19）

实机确认原路径的快速连续移动只有约 18–19 次绘制/秒；主要开销是逐帧重采样及更新每张图标时的自动拉伸/布局检查。保留图标内容、整数尺寸、圆屏投影、边缘渐隐、阻尼和回弹规则，不通过减少尺寸档位换取帧率。

- 已经按目标尺寸重采样的图标改用居中原尺寸绘制，避免 `STRETCH` 在替换图像源与更新控件大小之间再次缩放、强制检查全局布局。没有工作缓冲时仍沿用拉伸回退，避免内存不足时显示裁切。
- 启动阶段复用原插值器预计算尺寸，以逐行 RGB565 游程压缩保存，缓存只使用 PSRAM，硬上限 1.5MiB，优先缓存较大的尺寸。缓存缺失/不足/分配失败均退回原缩放路径；拖动期不新增缓存分配。恢复只写有效像素，保持行跨度与填充字节，不降低颜色或缩放精度。
- 每枚位图的位置和尺寸合并为一次样式刷新，避免四个属性各自触发布局处理；刷新完成后恢复 LVGL 样式更新。
- 代价：缓存版本启动预计算约 1.4 秒，空闲 PSRAM 从约 4.62MB 降到约 3.05MB。未新增任务或依赖，不增加内部 DMA 缓冲。

测量方法：临时测试固件在相同设备上以 10ms 定时器请求移动，轨迹为 `x=180*sin(9*t)`、`y=160*cos(7*t)`，每条路径运行约八秒；记录 LVGL `RENDER_READY` 次数、布局/缩放/绘制累计耗时及最长布局耗时。此值是自动轨迹的程序绘制吞吐量，包含绘制回调及刷新等待，不等同于屏幕实际呈现帧率或真人触摸到显示的时延。测试全程音量为 0，无外放。

同一固件最后一组八秒对照：

| 路径 | 绘制次数 / 耗时 | 绘制吞吐量 | 平均布局 | 最长布局 |
| --- | --- | --- | --- | --- |
| 原自动拉伸 + 原缩放 | 151 / 8.046s | 18.8 次/秒 | 36.0ms | 58.5ms |
| 居中原尺寸 + 合并刷新，无缓存 | 243 / 8.032s | 30.3 次/秒 | 16.7ms | 48.7ms |
| 居中原尺寸 + 合并刷新 + 缓存 | 318 / 8.020s | 39.7 次/秒 | 8.9ms | 16.2ms |

最终版本缓存 337 个图标尺寸，共使用 1572858 字节（包含索引与游程），预计算 1435ms；该容量优先覆盖计算较重的大尺寸，小尺寸缺失仍精确插值。相对原路径绘制吞吐量约为 2.1 倍；只代表上述自动轨迹，不能宣称所有实机手势都稳定 40/60 帧。

- Mimi 的 TTS Opus 包按接收顺序进入有界队列（64 包，每包最多 2048 字节，包体放 PSRAM），由已有语音任务解码为 16kHz 单声道 PCM 并复用扬声器播放。WebSocket 回调不解码、不阻塞等待播放；失败或队列满显示「语音播放失败」，结束本轮会话，避免静默丢包。

- 实机捕获左滑时 `allocate DMA buffer failed`，随后空指针 `LoadProhibited`；ELF 解码为 `i2s_rx_channel_start → i2s_channel_enable → _i2s_data_enable → esp_codec_dev_open → open_audio`。BSP DMA 从默认 240 帧缩为 120 帧，双声道每块 480 字节、6 块覆盖约 45ms，减少内部 RAM 需求。
- 配置阶段幂等修补托管音频库：数据接口配置失败不继续启动通道，启动失败清除打开标记并返回；配对 TX 配置失败不继续启用。补丁在 `ui_demo/main/CMakeLists.txt`，重新获取依赖后自动应用，不依赖手工编辑托管文件。

### 3S 英语儿歌页

入口：**表盘左滑**；页内**右滑**回表盘（不叠返回按钮）。页面内上滑切换到「本周曲库」卡，下滑回播放器卡。

| 能力 | 实现 |
|---|---|
| 曲库 | 启动后后台拉取 `http://<曲库服务器>:8083/family/modules/nursery/data/songs.js`（455 首，最多解析 512 首），不写入 Flash |
| 播放 | 每首 MP3 通过 HTTP Range 流式读取 → `esp_audio_simple_dec` 解码 → 44.1kHz 立体声线性重采样到 16kHz 单声道 → ES8311 外放 |
| 播放模式 | 列表循环 / 单曲循环 / 随机；上一首、下一首、播放/暂停 |
| 本周曲库 | 以 `nursery-v1` 为盐值按周生成 4–5 首；每周六 0 点自动刷新，同一周各设备结果一致；长按曲目可换歌（打卡中拒绝） |
| 打卡 | 早 / 午 / 晚三场，目标 40 / 10 / 40 分钟；点按开始或暂停，长按结束；早+晚都完成记 1 星，集满 5 星兑换 1 张愿望卡 |
| 持久化 | 打卡记录、本周曲库、音量写 NVS，重启不丢 |
| 互斥 | 儿歌播放与语音聊天共用 I2S，同一时间只允许一个方向；进入儿歌页会先停掉录音 |

歌词按 `lyrics/<id>.json` 拉取并缓存最近一首；播放失败的短状态显示在播放器卡片底部。

### 豆包宠物状态桥（可选）

宠物页默认用**本地情景引擎**（电量 / 充电 / 网络 / 时间 + 7 句英语台词轮换）。要把豆包回复映射成宠物表情，加一个服务端 JSON 接口即可；**设备端不保存任何云 Key**：


menuconfig → `English Pet Watch UI Demo` → `Doubao pet bridge URL` 填 `http://<电脑IP>:8788/pet/state`，轮询间隔默认 8000ms（`EPW_PET_BRIDGE_INTERVAL_MS`）。

### 豆包语音链路（xiaozhi-server WebSocket）

设备端实现见 `ui_demo/main/voice_client.c`，按 xiaozhi-esp32 `websocket_zh.md` 的 **v1** 协议：

- 上行：ES7210 麦克风 → PCM 16kHz/单声道/16bit → Opus 60ms 帧 → WebSocket 二进制帧；
- 下行：接收文本事件显示表情与台词；TTS 二进制帧直接丢弃，当前不解码、不播放；
- 文本事件：`hello` 建会话、`stt` → 宠物「思考」、`llm` 的 `emotion`/`text` → Mimi Cat 表情与气泡、`tts` 控制上下行；
- 鉴权 token 只从本地 Kconfig 读取，不保存云 Key。

配置（写进 `firmware/epw.env`，由 `tools/sync_env.sh` 生成 `sdkconfig.local`；留空 = 关闭语音链路）：

```text
EPW_VOICE_WS_URL='ws://<服务器IP>:8818/xiaozhi/v1/'
EPW_VOICE_TOKEN=''
```

编译/烧录命令同上；串口验证顺序：

```text
宠物页左滑请求聊天
服务器完成 hello 握手
epw-voice: microphone active (16 kHz mono)
退出/熄屏后：epw-voice: voice session stopped; microphone closed
```

> 语音链路依赖 Wi-Fi 与服务端可达。2026-11-17 实测：`vls` 上 xiaozhi 容器在跑（`127.0.0.1:8000/8003`），
> 但 nginx `5801` 未监听、安全组未放行（外网 `nc <服务器IP> 5801` 超时）；
> 打通公网入口前，设备会停在「等 Wi-Fi / 等 WebSocket」阶段，不会崩。

## 3. 编译

```bash
# 1. 安装并激活 ESP-IDF（每次新终端都要 source）
. <你的ESP-IDF>/export.sh
idf.py --version          # 已验证 v6.0.2

# 2. 进入本目录
cd projects/english-pet-watch/firmware
idf.py set-target esp32s3

# 3. 配置 Wi-Fi、型号和 OTA 地址
idf.py menuconfig
#   English Pet Watch ->

# 4. 编译
```


## 5. 发布一次 OTA

服务端只认这个文件名：`{device-model}_{version}.bin`。

```bash
# 1. 提升版本号：改 CMakeLists.txt 里的 PROJECT_VER，例如 0.2.0
idf.py build

# 2. 发布到服务器 data/bin（主机/目录读 firmware/epw.env 的 EPW_SERVER_HOST / EPW_SERVER_BIN_DIR）
./tools/publish_firmware.sh build/english_pet_watch.bin 0.2.0

# 3. 板子还没到？先用电脑模拟设备（URL 读 epw.env 的 EPW_OTA_URL，也可显式传参）
./tools/ota_probe.sh
```

预期响应里 `firmware.version = "0.2.0"`、`firmware.url` 指向 `/xiaozhi/ota/download/epw-watch-175_0.2.0.bin`。

> ⚠️ 服务端 `server.vision_explain` 必须写成**设备能访问的公网/局域网地址**，否则下载 URL 会变成 Docker 容器内网 IP。
> 见 `../software/host/vls/smoke.config.yaml` 的 `vision_explain`。

## 8. 常见故障

| 现象 | 原因 | 处理 |
|---|---|---|
| `还没有配置 Wi-Fi` | menuconfig 里 SSID 为空 | 填 SSID/密码，重编重烧 |
| 一直 `等待 Wi-Fi 连接超时` | 5GHz 热点 / 密码错 / 信号弱 | 用 2.4GHz；核对密码；靠近路由器 |
| OTA 返回 HTTP 500 | 缺 `device-id`/`client-id` 头 | 确认跑的是本目录固件，不是旧固件 |
| `已是最新固件` 但发了新 bin | 文件名前缀不等于 `device-model`，或版本号没变大 | 文件名必须是 `epw-watch-175_x.y.z.bin`；版本数字要比设备大 |
| 下载 404 | `vision_explain` 没配公网地址 / nginx 没转发 `/xiaozhi/ota/download/` | 改服务端配置，重启容器；检查 nginx |
| OTA 后花屏/反复重启 | 新固件本身有问题或分区表不匹配 | USB 重新烧录上一版 bin |
| 编译找不到 `esp_https_ota.h` | IDF 版本过低 | 升级到 6.0.1+，`idf.py fullclean` 后重编 |
